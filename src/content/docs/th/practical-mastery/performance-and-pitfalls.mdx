## type มี cost ตอน compile

การ type check คือการคำนวณจริง และ type ที่ฉลาดเกินไปทำให้ `tsc` คลานหรือ editor หน่วงได้ type system (ที่ขึ้นชื่อว่า) ทรงพลังพอที่จะเป็นภาษาโปรแกรมของตัวเอง — และเหมือน runtime code คือเขียนแบบที่ evaluate แพงได้เหมือนกัน

ตัวการที่พบบ่อย:

- **union ขนาดใหญ่** union ของ string literal เป็นพัน ๆ ตัว (มักถูก generate) ทวีคูณงานทุกที่ที่ถูกใช้
- **recursion ลึก** recursive conditional/mapped type ที่เดิน tuple หรือ string ยาว ๆ ชน exponential blow-up และ instantiation-depth limit
- **distributive conditional บน union ใหญ่** conditional type distribute บนทุก member — บน union ใหญ่ก็คือ instantiation จำนวนมาก
- **inference ที่ทำงานหนักเกินไป** API ที่ generic มากบังคับให้ checker แก้หา type argument หลายตัวในทุก call

คุณมักไม่สังเกตจนกว่าไฟล์หนึ่งใช้เวลา check เป็นวินาที หรือ red squiggle ใน editor ตามการพิมพ์ไม่ทัน นั่นคือสัญญาณให้มองที่ type ไม่ใช่แค่ code

## TypeScript 7 แก้อะไรได้ — และแก้อะไรไม่ได้

native compiler (7.0, กรกฎาคม 2026) ทำให้การ check *ทั้งโปรแกรม* เร็วขึ้น 8–12 เท่า และลดเวลาที่ editor ใช้ก่อนเห็น error แรกจาก 17.5 s เหลือราว 1.3 s บน codebase ของ VS Code มันทำได้ด้วย checker แบบขนาน (`tsc --checkers 4` เป็น default; release blog แนะให้ลดเหลือ `--checkers 1` บน CI runner ที่ core น้อย ส่วนเครื่อง local ที่ใหญ่กว่าเพิ่มได้เอง — ไม่มีเลขเพดานเจาะจง) และ native file watcher คำแนะนำเก่าที่ว่า "เอา `tsc` ออกจาก hot path เพราะมันช้า" จึงหมดอายุแล้ว — รันมันทุกครั้งที่ save ได้เลย

สิ่งที่มัน **ไม่ได้** แก้คือ type ที่ผิดธรรมชาติ instantiation แบบ exponential ก็ยัง exponential ใน Go เหมือนกัน recursive conditional type ที่เคยใช้ 30 s ใน TypeScript 6 ใช้ไม่กี่วินาทีใน 7 และยังกินเวลา build ส่วนใหญ่อยู่ดี และ union 5,000 member ก็ยังทวีคูณทุก operation ที่แตะมัน มีสองเรื่องที่เกี่ยวกัน:

- 5.9 cache type instantiation ระหว่างทาง ซึ่งกำจัด error "excessive depth" ส่วนใหญ่ใน library หนัก ๆ อย่าง Zod และ tRPC ถ้าคุณยังเจออยู่ แปลว่า type นั้นลึกเกินไปจริง ๆ
- editor check region ที่มองเห็นก่อน (region-prioritised diagnostics, 5.6) — squiggle โผล่ในสิ่งที่คุณกำลังดูภายในเสี้ยวของการ check เต็ม — ดังนั้น *editor* ที่หน่วงแทบทุกครั้งหมายถึง type ที่แพงใน *ไฟล์ที่เปิดอยู่* ไม่ใช่ทั้งโปรเจกต์

## footgun ที่พบบ่อย

นอกจาก performance เหล่านี้กัดทีมจริง:

- **type ฉลาดเกินจนไม่มีใครอ่านออก** conditional type 40 บรรทัดที่ประหยัด duplicate ไปสามบรรทัด มักขาดทุนสุทธิ ความฉลาดคือ cost ที่ผู้อ่านในอนาคตทุกคนต้องจ่าย
- **`any` leak** `any` ตัวเดียวลาม: `any.foo` เป็น `any` จึงปิดการ check เงียบ ๆ ทุกที่ที่แตะ แบนด้วย `noImplicitAny` และ lint rule
- **cast ที่โกหก** `x as Foo` บอก compiler ให้เลิก check — ถ้า `x` ไม่ใช่ `Foo` จริง คุณเพิ่งซ่อน bug ไว้ double cast (`x as unknown as Foo`) คือธงแดงขนาดยักษ์
- **เรื่องเซอร์ไพรส์ของ enum** numeric `enum` ยอมให้ number อะไรก็ได้เป็น value และ emit runtime code; `const` object กับ `as const` หรือ string-literal union มักชัดกว่าและถูกกว่า
- **ใช้ `as` เกินจำเป็น** การคว้า `as` มา silence error มักหมายความว่าคุณเลิก model ปัญหาแล้วเริ่มเถียงกับ compiler

## การเปลี่ยนล่าสุดที่ทำให้ error ใหม่โผล่

การ upgrade compiler บางครั้งเปลี่ยน code ที่เคยเงียบให้กลายเป็น error นี่คือรายการที่คนเจอในปี 2025–2026 และทุกข้อคือ checker ที่ถูกต้อง:

- **`ArrayBuffer` ไม่ใช่ supertype ของ typed array อีกต่อไป (5.7)** `Uint8Array` เป็น generic บน buffer ของมัน ดังนั้น function ที่รับ `ArrayBuffer` จะปฏิเสธ `Uint8Array` (และ `Buffer` ของ Node) มีสอง remedy ที่ไม่เท่ากัน: type parameter เป็น `Uint8Array<ArrayBuffer>` (หรือกว้างกว่าคือ `ArrayBufferLike`) ถ้าแก้ signature ได้ — หรือส่ง `data.buffer` แทน แต่ใช้ได้เฉพาะเมื่อ `data` เป็น `Uint8Array<ArrayBuffer>` เท่านั้น; `Uint8Array` ธรรมดามี `.buffer` เป็น `ArrayBufferLike` (อาจเป็น `SharedArrayBuffer` ได้) ดังนั้น `.buffer` เฉย ๆ ไม่พอสำหรับ parameter ที่ type เป็น `ArrayBuffer` ตรง ๆ
- **check ที่ truthy เสมอเป็น error (5.6)** `if (/regex/)` หรือ `if (x => 0)` ถูก flag เช่นเดียวกับ `a < b ?? c` ที่ฝั่งซ้ายไม่มีวัน nullish
- **แต่ละ branch ของ `return` ถูก check แยกกัน (5.8)** `return cond ? untyped.get(k) : "fallback"` เคยถูก `any` ใน branch หนึ่งบังไว้ ตอนนี้แต่ละ branch ต้องตรงกับ return type ที่ประกาศ
- **ตัวแปรที่ถูกใช้ก่อน initialise ถูกจับใน nested function (5.7)**
- **`infer` ใน template literal แยกตาม code point (7.0)** `HeadTail<"😀abc">` เป็น `["😀", "abc"]` — type ที่เคยสมมติว่าเป็นครึ่ง UTF-16 จะเปลี่ยน shape
- **JSDoc ในไฟล์ JavaScript เข้มขึ้น (7.0)** `@enum` แบบ Closure, type `?` เดี่ยว ๆ, postfix `!` และ `@class` ไม่ถูกยอมรับภายใต้ `checkJs` อีกต่อไป

## การ diagnose

เมื่อการ check รู้สึกช้า ให้วัดแทนการเดา:

- `tsc --extendedDiagnostics` พิมพ์ว่าเวลาและ memory ไปไหน (check time, instantiation count, memory)
- `tsc --generateTrace traceDir` สร้าง trace ที่เปิดใน profiler เพื่อหา type ที่แพงได้ รันพร้อม `--singleThreaded` เพื่อให้ตัวเลขไม่ถูกกระจายไปตาม checker worker
- `tsc --noCheck` บอกคุณว่า build ส่วนไหนเป็น emit และส่วนไหนเป็น check ถ้า `noCheck` ก็ยังช้า ปัญหาคือ I/O หรือ glob ใน `include` ไม่ใช่ type ของคุณ
- `skipLibCheck: true` ยังเป็นชัยชนะที่ถูกที่สุด: มันหยุดการ check ซ้ำทุก `.d.ts` ใน `node_modules`
- bisect: comment type ที่สงสัยออกแล้วดูตัวเลขขยับ

การแก้เกือบทุกครั้งคือ **simplify**: แทน conditional type ที่วีรบุรุษด้วย union ธรรมดา, แตก type ยักษ์เป็นชิ้นเล็กที่มีชื่อ หรือยอมรับ type ที่หลวมกว่านิดหน่อยแต่ถูกกว่า 10 เท่าและปลอดภัยพอ ๆ กันในทางปฏิบัติ

<Callout title="สรุปหนึ่งบรรทัด">
การ type check คือการคำนวณ union ใหญ่, recursion ลึก และ distributive conditional จึงทำให้ `tsc` และ editor ช้าได้ — และ native compiler แบบขนานของ TypeScript 7 ทำให้ *โปรแกรม* เร็วขึ้นสิบเท่าโดยไม่ได้ทำให้ *type* ที่ผิดธรรมชาติถูกลง footgun ประจำวัน — `any` ที่ leak, cast ที่โกหก, type ฉลาดจนอ่านไม่ออก และ numeric enum — ทำให้เสียทั้งความถูกต้องและความชัดเจน และ release ล่าสุดเปลี่ยนความผิดพลาดที่เคยเงียบหลายอย่าง (check ที่ truthy เสมอ, `ArrayBuffer` เทียบ typed array, branch ของ return ที่ไม่ถูก check) ให้เป็น error เมื่ออะไรช้า ให้วัดด้วย `--extendedDiagnostics` / `--generateTrace --singleThreaded` แล้ว **simplify**: type ที่อ่านออกและหลวมกว่านิดหน่อยมักชนะ type อัจฉริยะที่ไม่มีใคร maintain ได้
