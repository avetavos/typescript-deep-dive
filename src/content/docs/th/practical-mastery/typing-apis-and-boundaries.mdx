## ทุก bug เข้ามาที่ boundary

ภายใน code ของคุณเอง compiler คอยดูแลให้ bug แอบเข้ามาตรงที่ typed code เจอกับโลกที่ไม่มี type: response จาก network, `localStorage`, form, third-party library, `JSON.parse` ตรง edge เหล่านั้น การการันตีของ TypeScript ดีได้แค่เท่าที่คุณจัดการกับข้อมูลที่เข้ามา

การตัดสินใจแรกคือจะเลือก "ไม่รู้ type นี้" แบบไหน: `any` หรือ `unknown`

## `any` ปิด checker ส่วน `unknown` เก็บ checker ไว้

```ts
// @expect-error TS18046
declare const input: string;

const a: any = JSON.parse(input);
a.user.name.toUpperCase(); // compiles — and may explode at runtime

const u: unknown = JSON.parse(input);
u.user.name; // ❌ Error: 'u' is of type 'unknown'.
```

`any` opts *out* จากการ type check — เข้าถึงอะไรก็ได้ และการการันตีทั้งหมดถูกปิด `unknown` คือ top type ที่ซื่อสัตย์: รับ value อะไรก็ได้ แต่ห้ามคุณทำอะไรกับ value นั้นจนกว่าจะ **พิสูจน์** ว่าเป็นอะไร เลือก `unknown` ที่ทุก boundary และมอง `any` เป็น code smell ที่คุณกำลังกำจัดออกไป

สังเกตว่า `JSON.parse` ถูก type ให้ return `any` — ผลลัพธ์จึงแอบวางยา downstream ทั้งหมด เว้นแต่คุณจะ assign เป็น `unknown` ทันทีแล้ว validate

`catch` clause ก็คือ boundary เดียวกันในอีกหน้ากาก ด้วย `useUnknownInCatchVariables` — ซึ่งเป็นส่วนหนึ่งของ `strict` จึงเปิดเป็นค่าเริ่มต้นตั้งแต่ TypeScript 6.0 — ค่าที่ catch ได้เป็น `unknown` ไม่ใช่ `any` ดังนั้น `err.message` ต้องผ่าน `err instanceof Error` ก่อน

## เปลี่ยน `unknown` ให้เป็น type ที่เชื่อถือได้

การ narrow `unknown` ต้องใช้ runtime check ที่ compiler เข้าใจ สำหรับ shape ง่าย ๆ ใช้ **type guard** ที่เขียนเอง:

```ts
declare const input: string;

type User = { id: number; name: string };

function isUser(v: unknown): v is User {
  return (
    typeof v === "object" && v !== null &&
    "id" in v && typeof (v as any).id === "number" &&
    "name" in v && typeof (v as any).name === "string"
  );
}

const data: unknown = JSON.parse(input);
if (isUser(data)) {
  data.name.toUpperCase(); // ✅ data is User here
}
```

พอเป็นของจริง type guard ที่เขียนเองเริ่มน่าเบื่อและ drift ออกจาก type คำตอบมาตรฐานคือ **schema/parser library** (zod, valibot และเพื่อน ๆ) ที่ declaration เดียวเป็น *ทั้ง* runtime validator และ static type:

```ts
declare const input: string;
import { z } from "zod";

const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>; // static type derived from the schema

const data = User.parse(JSON.parse(input));
// data is typed User AND was checked at runtime — throws if invalid
```

source of truth เดียว, check ตอน runtime, infer ตอน compile time นี่คือ boundary ที่ทำถูก

## edge เพิ่มอีกสอง: ไฟล์ JSON กับวันที่

**JSON import** การ import ไฟล์ `.json` ให้ type ที่ได้มาจากเนื้อหาไฟล์โดยตรง — ไม่ต้องมี schema เพราะ compiler อ่านไฟล์ได้ ภายใต้ `--module nodenext` (TypeScript 5.7+) การ import ต้องมี attribute `type: "json"` และใช้ได้แค่ default import เท่านั้น ตรงตามที่ Node บังคับ:

```ts
// @skip-verify JSON module import needs resolveJsonModule and a json file
import config from "./config.json" with { type: "json" };
config.port; // typed from the file; named imports are an error
```

(ตรวจแยกนอก harness นี้: `tsc --module nodenext --resolveJsonModule` กับ `config.json` จริงที่มี `{ "port": 8080 }` compile ผ่านสะอาดเมื่อ access เป็น `config.port` ไม่ใช่ `config.default.port`)

สำหรับ config object ที่เขียนเอง `satisfies` เก็บ literal type ไว้พร้อมกับเช็ค shape:

```ts
const routes = { home: "/", user: "/users/:id" } satisfies Record<string, `/${string}`>;
routes.home; // still the literal "/" — not widened to string
```

**วันที่** TypeScript มี type ของ **Temporal** API อยู่ใน library `esnext` (`lib.esnext.temporal.d.ts` — ยังไม่ถูกรวมเข้า `es2025` ตรวจสอบแล้วกับ lib file จริงของเวอร์ชัน 7.0.2 ที่ติดตั้งอยู่) เมื่อ boundary ส่ง ISO timestamp มาให้ `Temporal.Instant.from(iso)` ให้ค่าที่ immutable และระบุ timezone ชัดเจน — เป็น type ภายในที่ดีกว่า `Date` ที่ mutable มาก และคาดว่า Node 26 จะเปิด Temporal เป็นค่าเริ่มต้น

```ts
const instant = Temporal.Instant.from("2026-09-22T00:00:00Z");
instant.epochMilliseconds; // type-checks
```

<Callout title="type compile ผ่านวันนี้ แต่ยังรันไม่ได้บน Node 24">
type declaration มีอยู่จริง แต่บน Node 24.13 ของคอร์สนี้ runtime ยังไม่มี: `globalThis.Temporal` เป็น `undefined` (ยืนยันด้วย `node -e "console.log(typeof globalThis.Temporal)"` → `undefined`) type ที่มาก่อน runtime ไม่ใช่เรื่องสมมติ — อย่าเชื่อว่า "compile ผ่าน" คือหลักฐานว่า API มีอยู่จริงจนกว่าจะเช็ค
</Callout>

## Branded type สำหรับ nominal ID

structural typing หมายความว่า `UserId` กับ `OrderId` ที่เป็น `string` ทั้งคู่ใช้แทนกันได้ — คุณจึงส่งตัวหนึ่งไปที่ที่คาดหวังอีกตัวได้ เมื่อเรื่องนี้สำคัญ ให้ **brand** type เหล่านั้นด้วย marker แบบ phantom:

```ts
// @expect-error TS2345
type UserId = string & { readonly __brand: "UserId" };

function getUser(id: UserId) { /* ... */ }

const raw = "u_123";
getUser(raw); // ❌ plain string is not a UserId
getUser(raw as UserId); // ✅ you deliberately asserted it at the boundary
```

brand มีอยู่แค่ตอน compile time (ถูก erase ทิ้ง), ไม่มี cost ตอน runtime และบังคับให้ทุก `UserId` ถูก *สร้างอย่างตั้งใจ* — โดยปกติคือทันทีหลัง validate นี่คือวิธีได้ nominal safety ในระบบที่เป็น structural

<Callout title="สรุปหนึ่งบรรทัด">
ทุก bug เข้ามาตรงที่ typed code เจอกับข้อมูลที่ไม่มี type เลือก `unknown` ไม่ใช่ `any` ตรง edge เหล่านั้น แล้วแปลงเป็น type ที่เชื่อถือได้ด้วย type guard หรือ (ดีกว่า) schema library อย่าง zod ที่ declaration เดียวเป็นทั้ง validator และ type สำหรับ ID ที่ห้ามปนกัน ใช้ **branded type** กฎคือเสมอ: validate ที่ edge, เชื่อภายใน
</Callout>
