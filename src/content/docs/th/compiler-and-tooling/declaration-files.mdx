## type ที่ไม่มี implementation

declaration file — `.d.ts` — คือไฟล์ที่มี **แต่ type ไม่มี runtime code** ใช้อธิบาย shape ของบางอย่างที่อยู่ที่อื่น: JavaScript library, global variable, module นี่คือวิธีที่ TypeScript รู้ type ของ code ที่ไม่ได้ compile เอง

คุณใช้ไฟล์พวกนี้ตลอดโดยไม่รู้ตัว เมื่อคุณ import `fs` ใน Node แล้วได้ autocomplete นั่นคือ `.d.ts` เมื่อ `document.querySelector` มี type นั่นคือ `lib.dom.d.ts` ตัว type กับ implementation เป็นไฟล์แยกกัน

## `declare` และ ambient declaration

keyword `declare` แปลว่า "เชื่อผมสิ ตัวนี้มีอยู่จริงตอน runtime — นี่คือ type ของสิ่งนั้น" keyword นี้แนะนำ **ambient** declaration: type ที่ไม่มี implementation แนบมา

```ts
// globals.d.ts
declare const APP_VERSION: string;      // injected by the bundler at build time
declare function gtag(...args: any[]): void; // a global from a script tag

// now usable anywhere, fully typed, with no import
console.log(APP_VERSION);
gtag("event", "page_view");
```

ถ้าไม่มี `declare` การเขียน `const APP_VERSION: string` จะเป็น *value* declaration และ compiler จะคาดหวัง initializer และ emit code ออกมา `declare` บอกว่า: นี่เป็นแค่คำสัญญาเรื่อง type ล้วน ๆ ไม่ต้อง emit อะไร

## การ type library ที่ไม่มี type

สมมติคุณ install JavaScript library เล็ก ๆ ที่ไม่มี type คุณอธิบาย shape ของตัวเองได้ด้วย module declaration:

```ts
// legacy-lib.d.ts
declare module "legacy-lib" {
  export function parse(input: string): { ok: boolean; value: number };
  export const version: string;
}
```

ตอนนี้ `import { parse } from "legacy-lib"` มี type ครบ แม้ library จะ ship JavaScript ธรรมดามา คุณได้เติม contract ที่ขาดไปด้วยมือ

## DefinitelyTyped และ `@types`

ส่วนใหญ่มีคนเขียน declaration พวกนั้นให้คุณแล้ว **DefinitelyTyped** คือ repository ชุมชนขนาดใหญ่ของไฟล์ `.d.ts` สำหรับ JavaScript library หลายพันตัว publish ภายใต้ scope `@types/*`:

```bash
npm install --save-dev @types/lodash
```

เมื่อคุณ *import* package `tsc` จะหา `@types/*` คู่ของมันใน `node_modules` ให้อัตโนมัติ การ install `@types/lodash` จึงทำให้ `import _ from "lodash"` มี type ทันที library สมัยใหม่หลายตัว ship type ของตัวเองมาใน package (declare ผ่าน field `"types"` ใน `package.json` ของตัวเอง) ซึ่งกรณีนั้นคุณไม่ต้องใช้ package `@types` เลย

package ที่ให้ **global** แทนที่จะเป็น module — `@types/node` สำหรับ `process` และ `Buffer`, `@types/jest` สำหรับ `describe` และ `expect` — เป็นอีกเรื่องตั้งแต่ TypeScript 6.0 default ของ `types` ตอนนี้คือ `[]` จึงไม่ถูกโหลดแค่เพราะ install ไว้ ต้องระบุ:

```json
{ "compilerOptions": { "types": ["node", "jest"] } }
```

(`"types": ["*"]` คืนพฤติกรรมโหลดทุกอย่างแบบเดิม) การเปลี่ยนนี้หยุดโปรเจกต์จากการแอบดึง package `@types/*` ที่ไม่เกี่ยวข้องเป็นร้อยจาก transitive dependency ซึ่งทั้งช้าและเป็นต้นตอของ error "duplicate global"

## ไฟล์ lib และการแทนที่มัน

ไฟล์ `.d.ts` built-in ของ platform — `lib.es2025.d.ts`, `lib.dom.d.ts` — ถูกเลือกด้วย `target` และ `lib` มีการเปลี่ยนสองเรื่องล่าสุด: `lib.dom.d.ts` ตอนนี้รวมทุกอย่างที่เคยแยกอยู่ใน `dom.iterable` และ `dom.asynciterable` (entry พวกนั้นเป็น stub ว่างที่เก็บไว้ให้ config เก่า) และ declaration ของ DOM มี summary จาก MDN ติดมาด้วย hover จึงแสดงคำอธิบายบรรทัดเดียวของแต่ละ API

ถ้า `lib.dom` ที่มากับ compiler ไม่ตรงกับคุณ — เก่าเกินไป หรืออยากใช้ type ของ `@types/web` — `libReplacement: true` (5.8) ทำให้ `tsc` หา package `@typescript/lib-dom` ใน `node_modules` แล้วใช้แทน ปิดเป็น default ตั้งแต่ 6.0 เพราะโปรเจกต์ส่วนใหญ่ไม่เคยต้องใช้ และการค้นหาเสียเวลา

## การ emit declaration ของตัวเอง

ถ้าคุณ publish library ที่เขียนด้วย TypeScript คุณอยาก ship ไฟล์ `.d.ts` เพื่อให้ผู้ใช้ *ของคุณ* ได้ type เปิดการ emit สำหรับ declaration:

```json
{ "compilerOptions": { "declaration": true } }
```

ตอนนี้ `tsc` ผลิต `.d.ts` ไว้ข้าง ๆ `.js` ที่ emit แต่ละไฟล์ แล้วคุณชี้ field `"types"` ใน `package.json` ไปที่ entry declaration ผู้ใช้ของคุณ import library แล้วได้ type information ครบ — กลไกเดียวกับที่ทั้ง ecosystem ใช้

มีสอง option ที่ทำให้สิ่งที่ emit ดีขึ้น:

- **`isolatedDeclarations`** (5.5) บังคับให้ทุก export มี type ระบุชัด แลกกับการที่ไฟล์ `.d.ts` generate ได้ทีละไฟล์โดยไม่ต้องรัน checker — แบบขนาน หรือให้ bundler plugin ทำ — ซึ่งเป็นสิ่งที่ monorepo ใหญ่ ๆ และเครื่องมืออย่าง `esbuild` ต้องการเพื่อ emit declaration ได้เร็ว
- ตั้งแต่ 5.8 computed property ที่ key เป็น identifier ธรรมดาหรือชื่อแบบมีจุดถูก **คงไว้** ใน declaration output แทนที่จะถูก widen เป็น index signature ทั่วไป:

```ts
declare const propName: string;
export const config = {
  [propName]: 1,
};

declare const ns: { key: string };
export const config2 = {
  [ns.key]: 2,
};

// tsc --declaration emits:
//   export declare const config: { [propName]: number; };
//   export declare const config2: { [ns.key]: number; };
// (pre-5.8 this widened both to { [x: string]: number })
```

ผู้ใช้จึงเห็น shape จริงแทนที่จะเป็น index signature เปล่า ๆ
