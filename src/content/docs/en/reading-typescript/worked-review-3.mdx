This review's domain is generics done at three different levels of confidence: a generic class whose own internals quietly give up on type safety, a generic parameter used correctly but exploited by variance, and a generic interface that never needed to exist at all.

interface UserRecord { id: number; name: string }

class DataCache<T> {
  private store: Record<string, any> = {}; // BUG 1: any -- the cache's own storage loses precision immediately
  set(key: string, value: T): void {
    this.store[key] = value;
  }
  get(key: string): T | undefined {
    return this.store[key];
  }
}

class Animal { speak(): string { return "..."; } }
class Dog extends Animal { bark(): string { return "woof"; } }
class Cat extends Animal { speak(): string { return "meow"; } }

function seedWithCat(cache: DataCache<Animal>): void {
  cache.set("pet", new Cat());
}

const dogCache = new DataCache<Dog>();
dogCache.set("pet", new Dog());
seedWithCat(dogCache); // BUG 2: variance -- DataCache<Dog> accepted where DataCache<Animal> is expected

interface Repository<T> {
  findById(id: number): T | undefined;
}

class UserCacheRepository implements Repository<UserRecord> { // BUG 3: single implementer, generic used once
  private cache = new DataCache<UserRecord>();
  save(id: number, record: UserRecord): void {
    this.cache.set(String(id), record);
  }
  findById(id: number): UserRecord | undefined {
    return this.cache.get(String(id));
  }
}

async function persistToRemote(entry: UserRecord): Promise<void> {
  await new Promise<void>((resolve) => setTimeout(resolve, 5));
  console.log("persisted:", entry.name);
}

function cacheAndPersist(repo: UserCacheRepository, entry: UserRecord): void {
  repo.save(entry.id, entry);
  persistToRemote(entry); // BUG 4: floating promise -- never awaited
}

const repo = new UserCacheRepository();
cacheAndPersist(repo, { id: 1, name: "Ada" });
console.log(repo.findById(1));

## Find the bugs before reading on

Two of these are generics-specific in a way the earlier reviews weren't; try to name all four before opening the answers.

<details>
<summary>Bug 1 — line 4, `private store: Record<string, any>`</summary>

**Symptom:** `DataCache<T>`'s own public API (`set(key, value: T)`, `get(key): T | undefined`) is perfectly precise — but its *internal* storage gave up on `T` entirely, typing every stored value as `any`.

**Evidence:** nothing crashes from this line alone in this program, but it is exactly what makes Bug 2 invisible from the inside: `this.store[key] = value` never complains no matter what actually gets assigned, because `any` accepts everything silently.

**Fix:** an actual generic container — `Map<string, T>` — keeps `T` precise all the way through:

```ts
// @skip-verify partial snippet, illustrates the fix only -- see the full fixed version below
class DataCache<T> {
  private store: Map<string, T> = new Map();
  set(key: string, value: T): void {
    this.store.set(key, value);
  }
  get(key: string): T | undefined {
    return this.store.get(key);
  }
}
```

</details>

<details>
<summary>Bug 2 — line 24, `seedWithCat(dogCache)`</summary>

**Symptom:** `dogCache` is a `DataCache<Dog>`; `seedWithCat` expects a `DataCache<Animal>`. TypeScript allows the assignment, because `set(key: string, value: T): void` is written in **method-shorthand syntax**, which is checked bivariantly — the exact same hole this course's variance lesson demonstrates on a hand-written `Stack<T>`.

**Evidence:** the real crash. `seedWithCat` pushes a `Cat` into what is, underneath, `dogCache` itself; `dogCache.get("pet")` later returns that `Cat`, typed as `Dog`, and `.bark()` throws.

**Fix:** if a function only needs to *read* from a generic container, accept a type that cannot be mutated through — here, a `ReadonlyMap<string, Animal>` — so there is no `set` to exploit in the first place:

```ts
// @skip-verify partial snippet, illustrates the fix only -- see the full fixed version below
function describeAnimals(cache: ReadonlyMap<string, Animal>): void {
  for (const animal of cache.values()) console.log(animal.speak());
}
```

</details>

<details>
<summary>Bug 3 — line 26, `interface Repository<T>` with one implementer</summary>

**Symptom:** `Repository<T>` is implemented by exactly one class, ever, and `T` appears in exactly one position (`findById`'s return type). It adds a second declaration a reader has to open to understand `UserCacheRepository`, for zero actual polymorphism.

**Evidence:** no crash, no diagnostic — the cost is purely structural. Nothing in this program ever accepts a `Repository<T>` where a concrete `UserCacheRepository` wouldn't do exactly as well.

**Fix:** delete the interface; keep the concrete class.

</details>

<details>
<summary>Bug 4 — line 45, `persistToRemote(entry);` with no `await`</summary>

**Symptom:** the remote-persistence call is fired and forgotten; `cacheAndPersist` returns immediately, before `persistToRemote` has done anything observable.

**Evidence:** `persisted: Ada` never printed in the real output — the process crashed on the unrelated cache-variance bug before the abandoned 5ms timer had a chance to fire.

**Fix:** `await` it, and make `cacheAndPersist` itself `async`:

```ts
// @skip-verify partial snippet, illustrates the fix only -- see the full fixed version below
async function cacheAndPersist(repo: UserRepository, entry: UserRecord): Promise<void> {
  repo.save(entry.id, entry);
  await persistToRemote(entry);
}
```

</details>

## The fixed version

```ts
// @run
interface UserRecord { id: number; name: string }

class DataCache<T> {
  private store: Map<string, T> = new Map();
  set(key: string, value: T): void {
    this.store.set(key, value);
  }
  get(key: string): T | undefined {
    return this.store.get(key);
  }
}

class Animal { speak(): string { return "..."; } }
class Dog extends Animal { bark(): string { return "woof"; } }
class Cat extends Animal { speak(): string { return "meow"; } }

function describeAnimals(cache: ReadonlyMap<string, Animal>): void {
  for (const animal of cache.values()) console.log(animal.speak());
}

const dogCache = new DataCache<Dog>();
dogCache.set("pet", new Dog());
// describeAnimals only reads, and only accepts a read-only view -- no way to sneak a Cat in

class UserRepository {
  private cache = new DataCache<UserRecord>();
  save(id: number, record: UserRecord): void {
    this.cache.set(String(id), record);
  }
  findById(id: number): UserRecord | undefined {
    return this.cache.get(String(id));
  }
}

async function persistToRemote(entry: UserRecord): Promise<void> {
  await new Promise<void>((resolve) => setTimeout(resolve, 5));
  console.log("persisted:", entry.name);
}

async function cacheAndPersist(repo: UserRepository, entry: UserRecord): Promise<void> {
  repo.save(entry.id, entry);
  await persistToRemote(entry);
}

async function main(): Promise<void> {
  const repo = new UserRepository();
  await cacheAndPersist(repo, { id: 1, name: "Ada" });
  console.log(repo.findById(1));

  const pet = dogCache.get("pet");
  console.log(pet?.bark());
}

main();
```

**Real output:**

```text
persisted: Ada
{ id: 1, name: 'Ada' }
woof
```

Every line runs in order, `persisted: Ada` prints before anything else waits on it, and `dogCache` still holds a real `Dog` — there was never a way to sneak a `Cat` into it.

`tsc --strict`: **zero errors**, on both versions.

`typescript-eslint`'s typed rules, run on the buggy version:

```text

9:5    error  Unsafe return of a value of type `any`                 @typescript-eslint/no-unsafe-return
46:3   error  Promises must be awaited, end with a call to .catch, end with a call to .then
               with a rejection handler or be explicitly marked as ignored with the `void`
```

Bug 1 (`any`) and Bug 4 (the floating promise) are caught directly. Bugs 2 and 3 are not: the variance hole is the same deliberate, documented unsoundness this course's [Generic Classes & Interfaces](/typescript/en/generics/generic-classes-and-interfaces/) lesson demonstrates, and no lint rule inspects whether a generic interface earns its abstraction — only `knip`'s unused-exports report, run on a real multi-file project, would even hint at Bug 3, by showing `Repository` referenced from exactly one place.
