## Types have a compile-time cost

Type checking is real computation, and clever types can make `tsc` crawl or your editor lag. The type system is (famously) powerful enough to be a programming language of its own — and just like runtime code, it can be written in ways that are expensive to evaluate.

The usual culprits:

- **Huge unions.** A union of thousands of string literals (often generated) multiplies work everywhere it's used.
- **Deep recursion.** Recursive conditional/mapped types that walk long tuples or strings hit exponential blow-ups and the instantiation-depth limit.
- **Distributive conditionals over big unions.** A conditional type distributes over every member — over a large union that's a lot of instantiations.
- **Over-eager inference.** Very generic APIs force the checker to solve for many type arguments at every call.

You rarely notice until a file takes seconds to check or the editor's red squiggles lag behind your typing. That's the signal to look at your types, not just your code.

## What TypeScript 7 does — and does not — fix

The native compiler (7.0, July 2026) made the *whole program* 8–12× faster to check and cut the editor's time-to-first-error from 17.5 s to about 1.3 s on the VS Code codebase. It gets there with parallel checkers (`tsc --checkers 4` by default; the release blog recommends dropping to `--checkers 1` on CPU-constrained CI runners, and only raising it on larger local machines — it doesn't name a specific ceiling) and a native file watcher. So the old advice "keep `tsc` out of the hot path because it is slow" has expired — run it on every save.

What it does **not** fix is a pathological type. Exponential instantiation is exponential in Go too; a recursive conditional type that took 30 s in TypeScript 6 takes a few seconds in 7 and still dominates your build, and a 5,000-member union still multiplies every operation that touches it. Two related notes:

- 5.9 caches intermediate type instantiations, which removed most of the "excessive depth" errors in heavy libraries such as Zod and tRPC. If you still see one, the type is genuinely too deep.
- Editors check the visible region first (region-prioritised diagnostics, 5.6) — squiggles appear in what you are looking at in a fraction of the full check — so a laggy *editor* almost always means an expensive type in the *open file*, not the project.

## The common footguns

Beyond performance, these bite real teams:

- **Over-clever types nobody can read.** A 40-line conditional type that saves three lines of duplication is usually a net loss. Cleverness is a cost paid by every future reader.
- **`any` leaks.** One `any` spreads: `any.foo` is `any`, so it silently disables checking across everything it touches. Ban it with `noImplicitAny` and lint rules.
- **Casts that lie.** `x as Foo` tells the compiler to stop checking — if `x` isn't really a `Foo`, you've just hidden a bug. Double casts (`x as unknown as Foo`) are a giant red flag.
- **Enum surprises.** Numeric `enum`s allow any number as a value and emit runtime code; a `const` object with `as const` or a string-literal union is usually clearer and cheaper.
- **`as` overuse.** Reaching for `as` to silence an error usually means you've stopped modeling the problem and started arguing with the compiler.

## Recent changes that surface new errors

Upgrading the compiler occasionally turns previously-silent code into errors. These are the ones people hit in 2025–2026, and all of them are the checker being right:

- **`ArrayBuffer` is no longer a supertype of typed arrays (5.7).** `Uint8Array` is generic over its buffer, so a function that takes `ArrayBuffer` rejects a `Uint8Array` (and Node's `Buffer`). Two remedies, not interchangeable: type the parameter as `Uint8Array<ArrayBuffer>` (or the broader `ArrayBufferLike`) if you can change the signature — or pass `data.buffer` only when `data` is itself a `Uint8Array<ArrayBuffer>`; a plain `Uint8Array`'s `.buffer` is typed `ArrayBufferLike` (it can be a `SharedArrayBuffer`), so `.buffer` alone does not satisfy a parameter typed as plain `ArrayBuffer`.
- **Always-truthy checks are errors (5.6).** `if (/regex/)` or `if (x => 0)` is flagged, as is `a < b ?? c` where the left side can never be nullish.
- **Branches of a `return` are checked individually (5.8).** `return cond ? untyped.get(k) : "fallback"` used to be masked by the `any` in one branch; now each branch must match the declared return type.
- **Variables used before initialisation are caught in nested functions (5.7).**
- **Template-literal `infer` splits by code point (7.0).** `HeadTail<"😀abc">` is `["😀", "abc"]` — a type that assumed UTF-16 halves will change shape.
- **JSDoc in JavaScript files is stricter (7.0).** Closure-style `@enum`, a bare `?` type, postfix `!`, and `@class` are no longer accepted under `checkJs`.

## Diagnosing it

When checks feel slow, measure instead of guessing:

- `tsc --extendedDiagnostics` prints where time and memory go (check time, instantiation counts, memory).
- `tsc --generateTrace traceDir` produces a trace you can open in a profiler to find the expensive types. Run it with `--singleThreaded` so the numbers are not split across checker workers.
- `tsc --noCheck` tells you how much of a build is emit versus checking; if `noCheck` is already slow, the problem is I/O or `include` globs, not your types.
- `skipLibCheck: true` is still the cheapest win: it stops re-checking every `.d.ts` in `node_modules`.
- Bisect: comment out suspect types and watch the numbers move.

The fix is almost always **simplify**: replace a heroic conditional type with a plain union, break a giant type into smaller named pieces, or accept a slightly looser type that's 10× cheaper and just as safe in practice.

<Callout title="The one-line takeaway">
Type checking is computation, so huge unions, deep recursion, and distributive conditionals can make `tsc` and your editor slow — and TypeScript 7's native, parallel compiler makes the *program* ten times faster without making a pathological *type* cheap. The everyday footguns — leaking `any`, lying casts, over-clever unreadable types, and numeric enums — cost you correctness and clarity, and recent releases turned several silent mistakes (always-truthy checks, `ArrayBuffer` vs typed arrays, unchecked return branches) into errors. When something is slow, measure with `--extendedDiagnostics` / `--generateTrace --singleThreaded`, then **simplify**: the readable type that's slightly looser usually beats the brilliant one nobody can maintain.
</Callout>
