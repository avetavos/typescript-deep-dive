## Every bug enters at a boundary

Inside your own code the compiler has your back. Bugs sneak in where typed code meets the untyped world: a network response, `localStorage`, a form, a third-party library, `JSON.parse`. At those edges TypeScript's guarantees are only as good as what you do with the incoming data.

The first decision is which "I don't know this type" you reach for: `any` or `unknown`.

## `any` disables the checker; `unknown` keeps it

```ts
// @expect-error TS18046
declare const input: string;

const a: any = JSON.parse(input);
a.user.name.toUpperCase(); // compiles — and may explode at runtime

const u: unknown = JSON.parse(input);
u.user.name; // ❌ Error: 'u' is of type 'unknown'.
```

`any` opts *out* of type checking — every access is allowed and every guarantee is off. `unknown` is the honest top type: it holds any value, but forbids you from doing anything with it until you **prove** what it is. Prefer `unknown` at every boundary; treat `any` as a code smell you're actively removing.

Note that `JSON.parse` is typed to return `any` — so its result silently poisons everything downstream unless you immediately assign it to `unknown` and validate.

`catch` clauses are the same boundary in disguise. With `useUnknownInCatchVariables` — part of `strict`, and therefore on by default since TypeScript 6.0 — the caught value is `unknown`, not `any`, so `err.message` must be earned with `err instanceof Error` first.

## Turning `unknown` into a trusted type

Narrowing `unknown` requires runtime checks the compiler understands. For simple shapes, a hand-written **type guard**:

```ts
declare const input: string;

type User = { id: number; name: string };

function isUser(v: unknown): v is User {
  return (
    typeof v === "object" && v !== null &&
    "id" in v && typeof (v as any).id === "number" &&
    "name" in v && typeof (v as any).name === "string"
  );
}

const data: unknown = JSON.parse(input);
if (isUser(data)) {
  data.name.toUpperCase(); // ✅ data is User here
}
```

For anything real, hand-written guards get tedious and drift from the type. The standard answer is a **schema/parser library** (zod, valibot, and friends) where one declaration is *both* the runtime validator and the static type:

```ts
declare const input: string;
import { z } from "zod";

const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>; // static type derived from the schema

const data = User.parse(JSON.parse(input));
// data is typed User AND was checked at runtime — throws if invalid
```

One source of truth, checked at runtime, inferred at compile time. This is the boundary done right.

## Two more edges: JSON files and dates

**JSON imports.** Importing a `.json` file gives you a type derived from its contents — no schema needed, because the compiler can read the file. Under `--module nodenext` (TypeScript 5.7+) the import must carry the `type: "json"` attribute, and only the default import is allowed, exactly as Node requires:

```ts
// @skip-verify JSON module import needs resolveJsonModule and a json file
import config from "./config.json" with { type: "json" };
config.port; // typed from the file; named imports are an error
```

(Verified separately, outside this harness: `tsc --module nodenext --resolveJsonModule` against a real `config.json` with `{ "port": 8080 }` compiles clean once the access is `config.port`, not `config.default.port`.)

For hand-written config objects, `satisfies` keeps the literal types while checking the shape:

```ts
const routes = { home: "/", user: "/users/:id" } satisfies Record<string, `/${string}`>;
routes.home; // still the literal "/" — not widened to string
```

**Dates.** TypeScript ships types for the **Temporal** API in the `esnext` library (`lib.esnext.temporal.d.ts` — not yet folded into `es2025`, verified against the installed 7.0.2 lib files). When a boundary hands you an ISO timestamp, `Temporal.Instant.from(iso)` gives you an immutable, timezone-explicit value — a far better inner type than a mutable `Date`, and Node 26 is expected to enable Temporal by default.

```ts
// @skip-verify Temporal lives in lib.esnext.temporal — this harness always compiles fences with --lib es2025; type-checked separately with --lib esnext,dom
const instant = Temporal.Instant.from("2026-09-22T00:00:00Z");
instant.epochMilliseconds; // type-checks
```

<Callout title="Type-checks today, doesn't run yet on Node 24">
The type declarations exist, but on this course's Node 24.13 the runtime doesn't: `globalThis.Temporal` is `undefined` (confirmed with `node -e "console.log(typeof globalThis.Temporal)"` → `undefined`). Types shipping ahead of the runtime isn't hypothetical here — never treat "it compiles" as proof an API exists until you check.
</Callout>

## Branded types for nominal IDs

Structural typing means a `UserId` and an `OrderId` that are both `string` are interchangeable — so you can pass one where the other is expected. When that matters, **brand** them with a phantom marker:

```ts
// @expect-error TS2345
type UserId = string & { readonly __brand: "UserId" };

function getUser(id: UserId) { /* ... */ }

const raw = "u_123";
getUser(raw); // ❌ plain string is not a UserId
getUser(raw as UserId); // ✅ you deliberately asserted it at the boundary
```

The brand exists only at compile time (it's erased), costs nothing at runtime, and forces every `UserId` to be *created deliberately* — usually right after validation. It's how you get nominal safety in a structural system.

<Callout title="The one-line takeaway">
Every bug enters where typed code meets untyped data. Reach for `unknown`, never `any`, at those edges, and convert it to a trusted type with a type guard or (better) a schema library like zod, where one declaration is both the validator and the type. For IDs that must not mix, use **branded types**. The rule is always: validate at the edge, trust inside.
</Callout>
